In the previous challenge the receivers bound straight to a `TinyMessage`, as if the sender had handed them the object directly. It didn't. Dapr wrapped that payload in a **CloudEvents** envelope on the way out, and `app.UseCloudEvents()` quietly unwrapped it on the way in. This challenge opens the envelope. This challenge takes about 5 minutes to complete.

## 1. What Dapr puts on the wire

[CloudEvents](https://cloudevents.io/) is a CNCF specification for describing event data in a common way, and it's the default message format for Dapr pub/sub. Every message you publish with the Pub/Sub API is wrapped in an envelope like this:

```json,nocopy
{
  "id": "5929aaac-a5e2-4ca1-859c-edfe73f11565",
  "source": "sender",
  "type": "com.dapr.event.sent",
  "specversion": "1.0",
  "datacontenttype": "application/json",
  "pubsubname": "demo5-pubsub",
  "topic": "incoming-messages-cloudevents",
  "traceid": "00-113ad9c4e42b51637366e73a934f4d24-b1a15e02b8d1a4c2-01",
  "data": {
    "id": "44444444-4444-4444-4444-444444444444",
    "timeStamp": "2026-01-01T12:00:00+00:00"
  }
}
```

Your payload sits in `data`. Everything around it is metadata Dapr filled in:

- **`id`** — a unique event ID, generated by Dapr. Not the same as the `id` inside your payload.
- **`source`** — the app ID of the publisher (`sender`).
- **`type`** — the event type. Dapr's default is `com.dapr.event.sent`.
- **`specversion`** and **`datacontenttype`** — required CloudEvents attributes.
- **`pubsubname`** and **`topic`** — Dapr extensions telling the subscriber where the event came from.
- **`traceid`** — the W3C trace context, so a published message stays part of a distributed trace.

Why does this matter? Because subscribers on the other side of a topic often need the metadata, not just the payload: to filter on `type`, to correlate on `traceid`, or to know which service produced the event. And because it's a standard, a non-Dapr consumer can read the same envelope.

## 2. Bind to the envelope instead of the payload

Open `Demo5-CloudEvents/ReceiverService/Program.cs` in the *Editor* tab:

```csharp,nocopy
var app = builder.Build();
// app.UseCloudEvents(); // Disabled to show CloudEvent payload
app.MapSubscribeHandler();

const string PUBSUB_NAME = "demo5-pubsub";
const string TOPIC_NAME = "incoming-messages-cloudevents";

app.MapPost("/messagehandler", [Topic(PUBSUB_NAME, TOPIC_NAME)](
    CloudEvent<TinyMessage> cloudEvent) => {
        Console.WriteLine($"Received CloudEvent of type: {cloudEvent.Type} from source: {cloudEvent.Source}.");

        var tinyMessage = cloudEvent.Data;
        Console.WriteLine($"Message received with ID: {tinyMessage.Id} at {tinyMessage.TimeStamp}.");

        return Results.Accepted();
});
```

Two changes compared to the receivers in challenge 1:

- **`app.UseCloudEvents()` is commented out.** That middleware replaces the request body with the contents of `data`, which is convenient but throws the envelope away.
- The handler binds **`CloudEvent<TinyMessage>`** instead of `TinyMessage`, so it can read `cloudEvent.Type` and `cloudEvent.Source` and still get the typed payload from `cloudEvent.Data`.

The `SenderService` publishes exactly as before — nothing special is needed to produce a CloudEvent:

```csharp,nocopy
await daprClient.PublishEventAsync(
    PubSubComponentName,
    TopicName,
    message);
```

```bash,run
cd Demo5-CloudEvents

```

> [!IMPORTANT]
> Wait until you see `Started Dapr with app id "receiver".` before continuing — the Dapr CLI prints one such line per app, and `receiver` is the last one to start.

Publish a message from the **curl** window:

```curl,run
curl -i --request POST --url http://localhost:5233/send --header 'content-type: application/json' --data '{"id":"44444444-4444-4444-4444-444444444444","timeStamp":"2026-01-01T12:00:00Z"}'
```

The **Dapr CLI** window should contain these application log statements:

```text,nocopy
== APP - sender == Sent message 44444444-4444-4444-4444-444444444444.
== APP - receiver == Received CloudEvent of type: com.dapr.event.sent from source: sender.
== APP - receiver == Message received with ID: 44444444-4444-4444-4444-444444444444 at 01/01/2026 12:00:00 +00:00.
```

The `type` is Dapr's default, `com.dapr.event.sent`, and the `source` is the publisher's app ID, `sender`. Neither of them appears anywhere in the application code.

## 4. Override a CloudEvent attribute

A default event type of `com.dapr.event.sent` is not much use to a subscriber that wants to route on it. You can override envelope attributes at publish time by passing metadata with keys prefixed `cloudevent.`.

Look at the second endpoint in `Demo5-CloudEvents/SenderService/Program.cs`:

```csharp,nocopy
app.MapPost("/sendwithmetadata", async (
    TinyMessage message,
    DaprClient daprClient) => {
        var metadata = new Dictionary<string, string>() {
            { "cloudevent.type", "special.type" }  // This overrides the built-in Dapr type
        };

        await daprClient.PublishEventAsync(
            PubSubComponentName,
            TopicName,
            message,
            metadata);
```

Publish to that endpoint from the **curl** window:

```curl,run
curl -i --request POST --url http://localhost:5233/sendwithmetadata --header 'content-type: application/json' --data '{"id":"55555555-5555-5555-5555-555555555555","timeStamp":"2026-01-01T12:00:00Z"}'
```

Expected application log statements:

```text,nocopy
== APP - sender == Sent message 55555555-5555-5555-5555-555555555555.
== APP - receiver == Received CloudEvent of type: special.type from source: sender.
== APP - receiver == Message received with ID: 55555555-5555-5555-5555-555555555555 at 01/01/2026 12:00:00 +00:00.
```

The event type is now `special.type`. The payload didn't change — only the envelope did.

> [!NOTE]
> `cloudevent.id`, `cloudevent.source`, `cloudevent.type`, `cloudevent.subject`, `cloudevent.datacontenttype` and `cloudevent.traceid` can all be overridden this way. Dapr will not let you replace `specversion`, and overriding `traceid` breaks trace correlation, so use it deliberately. See [Publishing and subscribing to CloudEvents](https://docs.dapr.io/developing-applications/building-blocks/pubsub/pubsub-cloudevents/) in the Dapr docs.

Stop the applications by pressing `Ctrl+C` in the **Dapr CLI** window, then go back up one folder:

```bash,run
cd ..
```

## 5. When you don't want the envelope

Two escape hatches are worth knowing about:

- **Publish your own CloudEvent.** If the payload you publish is already a valid CloudEvent, Dapr recognizes it and passes it through instead of wrapping it again. Handy when an upstream system already produces CloudEvents.
- **Turn the envelope off entirely.** Setting the `rawPayload` metadata value to `"true"` on publish (and on the subscription) sends the payload as-is. Use this when the consumer is a non-Dapr application that expects a bare message.
